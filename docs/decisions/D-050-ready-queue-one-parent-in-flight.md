# D-050 The Ready column is a queue: one parent in flight

Status: accepted 2026-11-23. Issues: MET-172 and MET-175, part of MET-171. Amends D-014 and D-040.

- `limits.max_parents` is a positive integer with default 1. It is in `LimitsConfig` and the defaults in `packages/shared/src/config.ts`, checked with the same `positiveInt` as `max_concurrent`. Zero, a negative number and a non-integer are a config error with the text `expected an integer >= 1`. It merges per layer like the other `limits` keys, so a workspace layer overrides the global one.
- A parent is in flight from its grill until it is Done, Canceled or Needs input. `max_parents` caps the parents in flight. The loop takes the top Ready parent in Linear's manual order (`sortOrder`, then priority, then oldest) and leaves the other Ready parents untouched.
- A Ready parent that cannot grill yet stays in Ready, with no move and no comment. It gets one log line per wait: `<key> waits, <in-flight key> is in flight`. With more than one parent in flight the keys join with `, ` and the line says `are in flight`. The loop keeps an in-memory map from the waiting id to the set of in-flight keys and logs again only when that set changes or the parent stops waiting and then waits again. A restart logs once more.
- Admission is by split record time, oldest first. The first `max_parents` in-flight parents are admitted, so when a human moves a parked parent back to Ready and the count goes over the limit, the earlier parent still finishes first. Parts of the other in-flight parents wait and get the same one-line wait log, with the part key. No new grill starts while the count is at or over the limit.
- `dispatchEligible` starts a part or a QA sub-issue only when its `parentId` is an admitted in-flight parent. A parent without a split record was not split by the loop, so its parts keep running as before. A part of a parent in Needs input does not start. Everything else in dispatch stays as it is: `blocks` relations, `max_concurrent`, per-part QA, reviewed heads and the token budget.
- It sits next to `limits.max_concurrent` and does not replace it. `max_concurrent` still caps agent runs at the same time; both limits hold.
- `harnessd init` writes a commented `# max_parents = 1` line next to `max_concurrent`, and docs/CONFIG.md "Limits and token spend" describes the key. docs/LOOP.md "Split" and "Dispatch" describe the queue, the wait line and the parent filter. SPEC "Autonomy loop" step 1 takes the top Ready issue in Linear's manual order, with priority as tie-break, and the SPEC "Limits" list names `max_parents`.

Why: the loop grilled and split every Ready parent in the same tick, so parts of two parents interleaved. `limits.max_concurrent` limits running agents, not parents. On 2026-11-23 another session moved three tickets to Ready during MET-87, MET-164 was grilled and split in parallel, and that run was wasted. The owner's rule is one ticket at a time: one PR, one review, one QA, merge, then the next ticket. The Ready column is the queue, so the owner orders the work on the board instead of holding tickets in Backlog.

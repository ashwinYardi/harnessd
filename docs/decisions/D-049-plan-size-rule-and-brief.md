# D-049 Plan size rule, area split and the fixed part brief

Status: accepted 2026-11-23. Issue: MET-162, part of MET-87. Amends D-040 (one part by default, the one-part fallback, a reason only for multi-part plans), D-044 (the fallback carries the grill calls) and D-045 (a turn-capped plan uses the fallback). Changes SPEC "Autonomy loop" step 4.

- **Size rule.** A ticket stays one part only when it is small: one area (backend or UI), about 3 Done-when items or fewer, and about 5 files or fewer. Otherwise it splits. A part is at most size M. `MAX_PLAN_PARTS` (6) stays the outer cap. The estimate-based part limit from the old MET-87 draft does not apply; D-040 superseded it.
- **Area split.** A ticket with backend and UI work gets separate parts. The backend part holds the shared types, the API and the daemon; it comes first and blocks the frontend part. The frontend part builds against the merged contract and runs on the frontend agent with its design checks. Docs changes go in the part whose code they describe, not in a separate docs part.
- **Shared files.** Parts that list the same file are chained with `blocks`, in plan order. Parts of one parent run one after another, so two open PRs never edit the same file.
- **Fixed brief shape.** Each part has `goal`, `doneWhen`, `files`, `steps`, `verify` and `outOfScope`, and all are non-empty. The part's Linear description shows, in this order: the marker, **Goal**, **Done when** (the covered parent items, copied as text), **Files**, **Steps**, **Verify** (each command with what its output must show) and **Out of scope**. **Decisions**, **Grill calls**, **Why**, **Spec links** and **Size** follow. The part's own Done when replaces the parent's full checklist. There is no free-text **Brief** section.
- **Plan check.** The loop rejects a plan where a part has an empty field, more than about 3 Done-when items or more than 8 files, or where one parent Done-when item is in no part. It also rejects a part that lists a file in the other area, a frontend part before a backend part, and a docs-only part in a multi-part plan. A rejected plan goes back to the coordinator once with every error. A second bad plan moves the parent to Needs input. This replaces the one-part fallback: there is no plan without a model.
- **Split note.** The parent's split comment lists each part with its key, role, size, goal and files, and the QA sub-issue with its blockers. It always ends with `Reason: <reason>`, for a split and for a one-part plan. The old "Reason for more than one part" line and the fallback line go away.
- **Builder prompt.** The part prompt starts with the brief sections, read from the part body, in the order above. The rules, decision ids, memory and other text come after them. A part body from before this change has no Goal section; its prompt keeps the full body as it was. The resumed send-back prompt (D-046) does not change.
- **QA.** QA reads the part's own Done when and Verify sections, not the parent's whole checklist. The verdict has one item per part Done-when item, plus one last item, `Verify`. In that item, QA runs each Verify command and quotes its result as evidence. The item count check uses this new count. A part body without these sections falls back to the parent's checklist. The daemon still runs `qa.test_command` first.
- **Merge gate (D-013).** The plan check proves that every parent Done-when item is in at least one part. Each part merges only after QA approves its own items. When every part has merged, every parent item has been approved. One item may appear in two parts; QA approves it in each part.

Why:
- The grill split MET-70 (2 points) into 5 parts and MET-63 into 4. Parallel parts edited the same files (MET-37 and MET-38 on `docs/INSTALL.md`; MET-76 and MET-77), and MET-109 became 4 parallel PRs that burned the Codex quota (MET-123). The old "one part by default" then failed the other way: MET-124 was one backend part with 9 Done-when items and a UI change, so the backend agent did UI work without the frontend design checks.
- The plan prompt asked only for a role, title, free-text prompt and size. A builder could get a vague task with no steps or way to verify it.
- Community practice for spec-driven agent work: turn the ticket into ordered small tasks with a check each; a task is too big past about 3 acceptance criteria, more than one subsystem or about 5 files; give an agent only its slice; check the plan before a build; land the contract before the UI.

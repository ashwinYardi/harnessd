# D-043 Weight the token budget by cache cost, and log turns per run
Status: accepted 2026-11-22. Issue: MET-139. Amends D-040, D-014 and SPEC "Limits". Part of MET-131.

- The token budget is a **weighted** sum: `input + output + round(cached × weight)`. `cached` is cache read plus cache write. The weight is `limits.cached_token_weight`, a number from 0 to 1, default **0.1**. The defaults become **S 3,000,000** and **M 6,000,000** weighted tokens. An unknown size still counts as M.
- The raw sums do not change. `loop.json` keeps `usage` and `usageBaseline` as input, cached and output, so old files load and the board's count stays the raw sum. Only the comparison with the budget and the Needs-input comment use the weighted total.
- The Needs-input comment states the weighted total and the budget, then the raw parts with the weight: `<n> of <budget> weighted tokens (<input> input + <cached> cached × <weight> → <weighted cached> weighted + <output> output)`.
- Each run's log line gains its turn count when the harness reports one: `<key>: <agent> used <input> input, <cached> cached, <output> output tokens in <n> turns`. OpenCode counts `step_start`, Codex counts `turn.completed`, and Claude Code reads `num_turns` from the result event. `turns` is in memory only; `loop.json` does not store it. A run with no count keeps the old line.
- A builder or QA worktree run gets a smaller skill set. `frontend` keeps `impeccable` and drops `grilling`, `domain-modeling`, `research` and `prototype`; `coordinator` keeps those four and drops `impeccable`; `backend` and `qa` drop all five. `enabled = false` still turns a skill off for everyone. MCP stays `harnessd-memory`. The builder prompt tells the agent to run focused tests and read file ranges, and that the issue is already grilled.
- `docs/LOOP.md` "What an agent run sees" holds the measured base prompt per harness, the MET-128 average per turn beside it, and OpenCode's truncation and compaction behaviour.

Why weighted tokens, not cost per harness:
- Codex reports no cost (D-032). OpenCode reports cost only for some providers (D-036). A price table per provider would be stale, and a missing cost would make the budget silently unlimited.
- A weight applies to every harness, needs no network and no pricing data, and one number in config explains the whole budget.
- Cached input is billed far below new input by every provider harnessd uses. Counting it in full made one 13-minute MET-128 build (186,944 input, 12,257,280 cached, 57,383 output) look like 12.5M tokens and trip the old M default of 12M before QA. At 0.1 the same build is **1,470,055** weighted tokens.
- The weight treats cache **writes** as cheap too. That undercounts only where a provider bills a write above input: Codex reports `cacheWrite` 0, and OpenCode's providers mostly report 0 or a write at or below input. Claude Code reports the most cache writes, and there the error is a small share of a run. Splitting read from write would need a second key and a second meaning for one number; the gain is small.
- The new M default fits the MET-128 arithmetic with room to spare: two builds of that size (2 × 1,470,055), one QA round (300,000 input + 20,000 output + 150,000 cached × 0.1 = 335,000) and 540,000 raw grill and plan tokens total **3,815,110** of 6,000,000. S is half of M, so a small ticket fits one build and one QA pass.

Measured base prompt (2026-11-22, this repo, OpenCode 2.3.2 on the owner's sign-in):
- The worktree sync writes about 47.8k chars a builder turn can see: AGENTS.md 4,509, the 9 remaining builder SKILL.md bodies 40,781, opencode.json 687, and the `harnessd-memory` tool list 1,878. At 4 chars a token that is about 12.0k tokens.
- One short real run's first `step_finish` reported 8,944 input plus 384 cache read: **9,328 tokens**. The same prompt in an empty folder, with no project files, took **7,437 tokens** (5,645 input + 1,792 cache read): that is OpenCode's system prompt and built-in tool schemas. The worktree files and the `harnessd-memory` tool list add about **1.9k tokens**. The static skill count is an upper bound because OpenCode exposes skills through its `skill` tool and loads a body only when it uses it.
- The MET-128 average was about **190k tokens per turn** (12,257,280 cached ÷ about 65 turns, plus the new input). So the base prompt is not what grows; the conversation and tool output are. OpenCode caps one tool result at `tool_output.max_lines` 2,000 and `max_bytes` 51,200 (about 50 KiB), and compacts automatically near the context limit: a summary replaces older conversation, about 15,000 recent tokens stay, and long tool output is shortened.
- No OpenCode option is added to the synced `opencode.json`. Its documented `tool_output` cap is already on, and a lower cap or a smaller `compaction.keep.tokens` would hide output the agent needs. The builder prompt asks for focused tests and file ranges instead.
- The owner's `~/.claude/skills` and `~/.agents/skills` hold 73,829 chars of SKILL.md bodies on this machine. OpenCode can load one when it uses that skill, and harnessd cannot remove them without breaking sign-in; that gap stays out of scope (D-036, MET-112).

After this merge, remove any stopgap `token_budget` override from `.harnessd/config.toml`: the coordinator set S 15M, M 30M when the old M budget ran out. At the new weight those values are almost unlimited, so they would hide the budget rather than raise it.
